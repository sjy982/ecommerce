# Ecommerce

Spring Boot 기반 Ecommerce 백엔드 프로젝트입니다.

이 프로젝트는 완성된 커머스 서비스를 만드는 것보다, Spring 기반 백엔드 애플리케이션의 주요 흐름을 직접 구현하며 내부 동작을 이해하고, 주문 처리 과정에서 발생할 수 있는 동시성·트랜잭션 문제를 경험해보기 위해 진행했습니다.

특히 한정 수량 상품에 주문이 몰리는 상황을 직접 재현해, 데드락·재고 정합성·커넥션 타임아웃 문제를 해결하고, 이후 남은 처리량 병목을 Redis로 개선하는 데 집중했습니다.

## 핵심 경험: 한정 수량 상품 동시 주문 처리

### 1단계. 동시 주문 시 95.8% 실패 → 0%

재고 1,000개 상품에 1,000건의 주문을 동시에 넣는 상황을 테스트했습니다.

초기에는 재고 차감, 결제 대기(3초), 주문 생성, 매출 반영을 하나의 트랜잭션에서 처리했고, **요청의 95.8%가 실패**했습니다. 원인은 하나가 아니라 세 가지였습니다.

| 원인 | 내용 |
|---|---|
| 데드락 | 주문 PK가 IDENTITY 전략이라 `INSERT orders`가 먼저 실행되어 FK 때문에 상품 row에 S-lock을 걸고, 커밋 직전 재고 `UPDATE`가 같은 row에 X-lock을 요구하며 서로를 기다림 |
| Lost Update | 락 없이 읽은 재고로 계산한 값을 더티 체킹이 통째로 덮어써서 차감이 유실됨 (주문 697건에 재고 402개만 차감) |
| 커넥션 풀 고갈 | 결제 3초가 트랜잭션 안에 있어 커넥션 10개를 3초씩 점유, 대부분의 요청이 커넥션 대기 타임아웃 |

이를 해결하기 위해 다음 두 가지를 적용했습니다.

- **비관적 락**(`SELECT ... FOR UPDATE`)을 트랜잭션의 첫 쿼리로 두어, 모든 트랜잭션이 같은 순서로 상품 row X-lock을 획득하도록 변경
- **결제를 주문 트랜잭션에서 분리**해, 주문 트랜잭션은 재고 차감과 `PENDING_PAYMENT` 주문, 결제 작업 저장까지만 하고 바로 커밋. 결제는 커밋 후 별도 스레드 풀에서 처리

락만 적용한 버전도 따로 측정해 보니, 데드락과 정합성은 해결됐지만 X-lock을 쥔 채 결제 3초를 기다려 **실패율은 96%로 그대로**였습니다. 두 조치가 각각 다른 문제를 해결한다는 것을 확인했고, 둘을 함께 적용해 **실패율 0%, 재고 정합성 확보**를 달성했습니다.

### 2단계. 핫 row 병목 → Redis 재고 판정

정합성은 확보했지만, 모든 주문이 **상품 row 하나의 락을 순서대로 통과**해야 해서 처리량이 약 140 TPS에서 막혔습니다. 재고 1,000개에 주문 3,000건이 몰리면 접수 완료에 6~8초, 품절 응답에 7~9초가 걸렸습니다.

- 커넥션 풀을 10 → 60개로 늘리면 오히려 140 → 126 TPS로 **느려졌고**, 결제 대기를 0초로 해도 같았습니다. 병목이 커넥션이나 결제가 아니라 상품 row 락이라는 것을 측정으로 확인했습니다.
- 분산락, 낙관적 락, 재고 버킷 분할 + `SKIP LOCKED` 등을 검토했습니다. 분산락은 정확성을 위한 도구라 직렬화는 그대로이고, 버킷 분할은 품절 요청까지 모두 DB를 거쳐야 해서 제외했습니다.

그래서 **재고 판정을 Redis로 옮겼습니다.**

- **Lua 스크립트**로 "재고 확인 + 차감"을 원자적으로 처리. 품절과 판매 전 요청은 DB에 가지 않고 바로 409로 응답
- 판매 중에는 상품 row를 UPDATE하지 않아, 주문 트랜잭션이 `INSERT`만으로 **병렬 커밋**
- Redis와 DB는 한 트랜잭션으로 묶을 수 없으므로, **"줄일 때 Redis 먼저, 늘릴 때 DB 기준"** 원칙으로 불일치가 생겨도 초과 판매가 아니라 "덜 팔림" 쪽으로만 생기게 설계
- DB 저장이 실패하면 `requestId`로 주문이 정말 없는지 확인한 뒤에만 Redis 재고를 되돌려, 커밋 결과를 알 수 없는 상황에서의 초과 판매를 방지
- 재고는 판매 오픈 API로 DB 기준 남은 수량을 계산해 Redis에 적재

### 결과

재고 1,000개에 주문 3,000건을 1초에 걸쳐 보낸 결과입니다. JMeter로 단일 장비에서 측정했습니다.

| 지표 | 개선 전 (DB 비관적 락) | 개선 후 (Redis 판정) |
|---|---|---|
| 1,000건 주문 접수 완료 | 6.2~7.8초 | 1.7~1.9초 |
| 주문 접수 TPS | 129~161 | 521~626 |
| 품절 응답 평균 | 7.6~9.3초 | 1.0~1.3초 |
| 초과 판매 / 에러 | 0 / 0 | 0 / 0 |

모든 회차에서 정확히 1,000건 접수, 2,000건 품절, 결제 1,000건 완료를 확인했습니다. 측정 방법과 스크립트는 [perf/README.md](perf/README.md)에 정리했습니다.

### 구현 중 만난 문제: 커넥션 풀 기아

H2 테스트는 모두 통과했지만, MySQL 부하 테스트에서는 **3,000건 중 30건만 성공**했습니다.

커밋 후 결제를 넘기는 `@TransactionalEventListener(AFTER_COMMIT)`에서 `REQUIRES_NEW` 트랜잭션으로 결제 작업 상태를 바꾸고 있었던 것이 원인입니다. 이 리스너는 같은 요청 스레드에서 동기로 실행되고, OSIV 때문에 원래 커넥션도 아직 쥐고 있어 **요청 하나가 커넥션 2개**를 필요로 했습니다.

결제 작업을 주문 트랜잭션 안에서 처음부터 처리 중 상태로 만들어, 커밋 후 요청 스레드가 DB에 다시 접근하지 않도록 바꿔 해결했습니다.

<br>

## 배운 점

- 하나의 증상 아래 여러 원인이 겹쳐 있을 수 있고, 원인을 분리해 하나씩 실험해야 각 조치의 효과를 증명할 수 있음
- JPA의 쓰기 지연, IDENTITY 전략, 더티 체킹이 실제 SQL 순서와 DB 락에 직접 영향을 줌
- 트랜잭션 안에 오래 걸리는 작업을 넣으면 커넥션 점유 시간이 길어지고, 락 안에 넣으면 처리가 직렬화됨
- 같은 처방(커넥션 증설)도 병목 위치에 따라 정반대 결과를 내므로, 측정으로 병목을 먼저 찾아야 함
- 두 저장소를 하나의 트랜잭션으로 묶을 수 없을 때는 실패가 어느 방향으로 생길지를 설계해야 함
- H2 테스트 통과만으로는 부족하고, 실제 DB와 부하 조건에서 확인해야 드러나는 문제가 있음

## 정리

이 프로젝트는 Ecommerce 도메인을 통해 Spring 기반 백엔드의 주요 흐름을 학습하고, 주문 처리 과정에서 발생할 수 있는 기술적 문제를 직접 경험하기 위해 진행했습니다.

완성된 서비스보다는 문제 상황을 재현하고, 원인을 분석하고, 측정으로 확인하며 구조를 개선하는 과정에 초점을 두었습니다.
